The golden path today

This full sequence works, end to end, against a real WhatsApp number and a real catalogue — verified live, not just in tests. It is the single strongest evidence of where the product stands.

Pharmacy connects WhatsApp

Owner enters a phone number, gets a pairing code, enters it on their phone. No QR, no Meta developer account, no App Review — Baileys links as a companion device in under a minute.

Owner uploads a catalogue spreadsheet

Messy real-world Excel is parsed, columns are auto-detected against a proven mapping engine ported from a sibling analytics product, and the owner reviews and confirms the mapping before a single product row is written.

Customer messages the shop

"I want the best antimalarial drug u have"

Assistant answers like a counter attendant, not a database

Narrows to the pharmacy's top picks, states real prices, and defers on anything clinical.

"They're all good ones we stock — here are my top picks: • Coartem — ₦1,970. Our pharmacist's pick... Which would you like?"

Customer orders; stock is held, not promised

Price and stock come only from the catalogue. Placing an order decrements stock immediately (a real hold, with a race-condition guard) — but the customer is told only that the order was sent. "Reserved" is never said until a human confirms.

Staff are alerted, on WhatsApp, and confirm

A configured staff number gets pinged with the order. Confirming in the dashboard is the one moment the customer is told anything is reserved for them — and only then.

A clinical question routes to a person, correctly

"Which one is good?" → "That's our pharmacist's judgement — would you like me to pass you to them?"

The pharmacist sees the customer's own words, quoted, on a triage queue — not a paraphrase — and gets a WhatsApp alert with a distinct alarm tone from the order chime.

Also fixed this build

The assistant used to echo the customer's own word for a unit — "paracetamol tablets at ₦460 per sachet" for a product that isn't sold in sachets. It now states the catalogue's own unit and corrects the customer explicitly: "That comes as tablets on a card, not a sachet — a card is ₦460." Grounded in data, not vocabulary borrowed from whoever's asking.

03

Safety & grounding design

The single biggest engineering bet in this codebase: the assistant is structurally unable to state a fact it cannot trace to the pharmacy's own data, and structurally unable to answer a clinical question. Four independent layers, not one prompt.

1

Deterministic filter, before the model sees anything

Regex-based clinical detection — dosage, symptoms, drug interaction, paediatric, pregnancy, overdose, prescription, clinical comparison ("which is better") — runs before the LLM is ever called. A model cannot be asked to police the exact input that would compromise its own judgement.

2

No catalogue knowledge to hallucinate from

The model holds no product data of its own. Every price, stock level, and description arrives as a tool result in that conversation or does not exist. Tenant id is bound server-side, never a model-visible parameter — a prompt injection can make the model ask for another pharmacy's data; it cannot make the SQL return it.

3

Reply validation after generation

Every number in a draft reply is checked against what a tool actually returned this conversation. Action claims ("I've reserved this", "I've notified the pharmacy") are checked against whether that action genuinely happened — catches the model's instinct to narrate the reassuring version rather than the true one.

4

Escalation is the default failure mode

No LLM key, a timeout, an unverifiable claim, a clinical trigger, too many tool iterations — every one of these hands the conversation to a person. There is no code path that ends in the assistant guessing.

What this caught, in real traffic

  • "Done, I've set aside 3 packs for you" — nothing was set aside. Fixed by building real stock reservation rather than just correcting the sentence.
  • "Which one is good?" between two antibiotics — a clinical comparison the original filter missed; caught in review and added as its own category.
  • Invented product descriptions — asked broadly about pain relief, the model wrote "Good for everyday pain relief" for a product with no description on file. Fixed by giving it a true fact to use instead (catalogue-derived factual_summary) rather than only telling it not to invent one.
  • Unit-of-sale drift — described above; the newest of these fixes.

Read honestly

Every one of these was found by generating real traffic and reading it, not by anticipating it in advance. That is the actual shape of hallucination prevention on a live product: layers that catch most things, plus a habit of reading transcripts.

Anti-ban / conduct design

Baileys is an unofficial channel. A banned number is the pharmacy's number, not ours — so the system is built to be structurally incapable of the behaviour that gets numbers banned, rather than merely instructed not to do it.

Architecture, for developers

Modular monolith: one Node process, one Postgres database, clear internal boundaries. No message queue service, no microservices — the volume does not justify the operational cost yet.

Stack

LayerChoice
WhatsApp channelBaileys (unofficial, WebSocket-based)
ServerNode.js, Express
DatabasePostgreSQL (Supabase-hosted), postgres driver
Background jobsPostgres-backed queue, in-process worker (no Redis)
LLMOpenAI-compatible chat API, tool-calling loop
ClientReact, Vite
AuthSupabase; dev bypass flag for local testing only

Patterns worth knowing before extending this

  • Decision logic lives in pure functions. disconnectPolicy, conductPolicy, ingestionPolicy, replyValidator, saleUnit — no database, no network, exhaustively unit-tested. The parts most likely to be got wrong are isolated from I/O specifically so they can be tested that way.
  • Tenant isolation is structural, not conventional. Every tool and query takes pharmacyId server-side; it is never a value the model or the client can set.
  • Persist before you process. Under Baileys nothing retries a dropped message on the product's behalf — the socket is not Meta's infrastructure. Inbound events are written durably before any interpretation happens.
  • Every drop is logged with a reason and enough context to debug it later — jid, age, message type — after two rounds of "the assistant isn't answering" that turned out to be silent, unexplained drops.

Test posture

460 tests, 0 failures at last run. The pure-function policy modules carry the heaviest coverage deliberately — that's where a wrong answer is expensive and silent. Live-traffic testing against the real assistant and a real WhatsApp number has been the primary way bugs in the AI layer were actually found; unit tests then lock the fix in.

What's not built yet

Live today

  • Full golden path above
  • Grounded conversational assistant
  • Real stock reservation
  • Pharmacist triage & alternatives
  • Anti-ban conduct controls

Known limitation

  • Baileys is unofficial — no Meta SLA, ban risk mitigated but not zero
  • One process per deployment — scaling model for many pharmacies not yet load-tested
  • No media (image/voice) handling in the conversation flow
  • No payment integration — cash/pickup only

Not started

  • Proactive/outbound messaging (deliberately out of scope on this channel)
  • Multi-language support
  • Analytics/reporting beyond the Overview screen
  • Automated regression testing of live AI replies (currently manual transcript review)

Recommended next

  • Run a real pharmacy on it, end to end, for a week. Every AI-layer bug found so far came from reading real transcripts, not from anticipating cases — that pattern should continue deliberately rather than by accident.
  • Decide the media-handling gap now, not when a customer sends a photo of a prescription. It's a real question with clinical-safety implications, worth designing rather than patching.
  • Load-test the single-process assumption before a second pharmacy signs up, so the scaling model is a plan rather than a surprise.
